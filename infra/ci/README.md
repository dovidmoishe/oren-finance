# Oren self-hosted CI

The owner authorized immediate migration on the current two-CPU / 7,424 MiB VPS, then deployment of PR #84 after its checks pass. The future three-CPU / 10 GB profile is retained as a reference; no upgrade is required for the current rollout.

## Execution and resource boundaries

- `oren-vps-build` / `oren-build` executes PR/CI/preview work under `oren-ci-build`. `oren-vps-release` / `oren-release` executes production image builds under a distinct `oren-ci-release` UID, home, rootless daemon and private local caches. Both retain the standard systemd user-slice layout required by rootless Docker. A root-owned Unix-socket admission service verifies peer UID and worker ownership/start time, admits at most two heavy jobs on different UIDs, and sets root-owned per-user slice limits: active 3,840 MiB / 100% CPU, inactive 512 MiB / 25% CPU, no swap. Two listeners on one UID are not two heavy jobs. Client disconnect does not release a live worker lease. After the worker exits, admission lowers CPU and MemoryHigh immediately and keeps MemoryMax at 3,840 MiB until cgroup usage plus 64 MiB is within 512 MiB. A cgroup still above the idle floor keeps its heavy slot. A free slot can still be admitted, and a third heavy job stays queued. It does not hard-shrink a live worker. A surviving PR process cannot read or modify release checkouts, processes, credentials, sockets or caches.
- `oren-vps-control-1` and `oren-vps-control-2` / `oren-control`: separate `oren-ci-control` account, aggregate 512 MiB / 25% CPU quota. They run trusted orchestration, polling gates and SSH deployments, never ordinary PR test/build code. This account is not spare build capacity.
- `oren-vps-light` / `oren-light`: one `oren-ci-light` runner, 768 MiB max / 768 MiB high / 100% CPU, no swap, no Docker, and not a member of `oren-ci-workers`. It runs the aggregate App check. App lint stays on `oren-build`: a frozen pnpm install is killed inside this 768 MiB cap and peaks at about 2.4 GiB on a 3,840 MiB cap. Lint still uses sequential 12-file chunks and the same eslint file set. A full eslint process peaked at 1,087 MiB and does not run on this lane. One file, one directory, and a 12-file chunk peaked at 432, 443, and 447 MiB as child RSS, which does not prove the full user slice fits 768 MiB. The light hook takes a permit from admission instead of sampling memory itself. On the ops-measured 13 GiB / 4 CPU host, two active 3,840 MiB heavy slices, one idle 512 MiB heavy slice, the 512 MiB control slice and the 768 MiB light slice sum to 9,472 MiB and leave 3,840 MiB. App test, app lint, Next build, API, preview infrastructure, and image builds stay on the heavy accounts. `oren-ci-build-2` is a second build UID with its own slice and rootless daemon. It is not the release account and it is not a second listener inside `oren-ci-build`.
- Trusted release/control job-start hooks require immutable GitHub runtime provenance from allowlisted master workflows before action pre-steps or container startup. Labels alone are not an authorization boundary. The runner constructs hook environment separately from workflow job env; see official JobHookProvider and JobExtension sources. PR jobs claiming trusted labels are rejected.
- Build users have no sudo or production Docker group. Production files and root SSH keys are inaccessible. UID/subuid egress rules reject production private subnets and metadata addresses; loopback test servers and public dependency/registry services remain available.
- Build services use umask 0022. API Docker builds explicitly normalize runtime-readable permissions while keeping root ownership; CI builds a restrictive-checkout fixture and tests migration readability as the image default node user. Controls retain umask 0077.
- Runner executables/configuration are root-owned; only work/log directories and tool caches are writable by the runner. Current official runner 2.338.2 uses its official runsvc.sh entry point and is checksum-pinned with auto-update disabled. Update the pinned release within GitHub's supported update window (normally 30 days after a new release), checking official digests and restarting only idle CI services.
- These are persistent, shared-kernel runners for this private repository's trusted collaborators. They do not provide disposable-VM isolation. Do not make the repository public or admit arbitrary untrusted code without revisiting the runner isolation model.
- Build admission waits for 4.5 GiB available host memory and 15 GiB free disk. Open previews are not stopped. If headroom does not recover, the CI job fails for retry rather than consuming production's reserve. Post-job cleanup removes only containers belonging to the dedicated rootless daemon and the verified CI workspace, preserving image/cache layers.

## Workflow behavior

All thirteen workflows route to the registered self-hosted labels. Every existing test/check and exact-SHA release gate is retained. API tests bind Postgres to a dynamic loopback port and provision roles with `docker exec`, without host networking. Preview fixture files live under runner temp; Compose defaults still point to deployed paths. Isolation-test Compose project names include run/job identifiers.

App test, Next build, API, and image work use the build lane. App lint and the aggregate App check use the light lane, so they do not occupy the single heavy worker. Lint still waits for host headroom and does not start when that would leave less than 1,792 MiB. Two control listeners prevent a single polling gate from blocking all orchestration. Preview and production image builds wait for their exact-SHA CI gate. GitHub still schedules the single heavy label in arrival order; this change does not add a priority queue, so a preview image build can still wait behind another heavy job. Production and docs release images use release-private local BuildKit caches, never PR-accessible GHA caches. Production deployment uses exact image digests returned by trusted builds, stores a server-side verified record after health checks, and checks running references against those digests. Rollbacks require that protected record; the pre-migration running release is seeded from actual container digests. Production API reuse from editable GitHub release notes is disabled. No optional fallback silently spends hosted runner minutes.

## Installation and validation

`provision.sh` installs official prerequisites, verified Node/GitHub CLI/runner distributions, unprivileged users, rootless Docker, narrow egress rules and bounded user services. It does not disable/restart production Docker, register runners or start financial features. Review the fixed account/path names before installation. Do not use it to roll the light lane onto the current host: it restarts admission and the heavy runners. Use `infra/ci/LIGHT-LANE-ROLLOUT.md` and `infra/ci/light-lane.sh` instead.

`register.sh` receives a short-lived repository registration token on stdin. It never stores a PAT or the registration token. It configures separate PR/release listeners and two control listeners, locks executable files to root ownership and starts only the CI services.

Run `bash infra/ci/validate.sh` on Linux for infrastructure tests and syntax checks. `capacity.mjs` remains a read-only JSON budget assessor; passing its arithmetic is not proof of network or controller enforcement. Validate actual cgroup memory/cpu files, production socket/file denial, private-network denial, real Actions checks and public readiness before declaring cutover complete.

The current server is slower than hosted parallel runners. Five or six PRs queue; newer commits cancel superseded checks per PR. The existing preview admission policy is independent of CI queue capacity. Future capacity upgrades should change only verified CI resource limits and admission thresholds, followed by a one-/two-job trial; do not infer resources from the provider slider or reboot production automatically.

## Recovery

Admission lets a verified successor reuse its own UID's draining heavy slot after the previous worker exits. Reclaim does not have to reach the idle floor first. The slot still counts toward the two-account limit, all active and draining caps count toward memory headroom, and a late drain cannot downshift a newly admitted worker. An account with a live lease cannot admit a second worker.

CI services run under the dedicated users' systemd managers. Stop/start them with `systemctl --user` under the corresponding account and XDG runtime directory. The rootless Docker socket is `/run/user/<build-uid>/docker.sock`; never substitute `/var/run/docker.sock`. Inspect `journalctl _UID=<uid>` and runner `_diag` logs. To undo routing, use a reviewed workflow change; do not leave required jobs targeting missing labels. Existing GitHub account billing restrictions may still affect hosted-only features; verify actual self-hosted runs.
